# 玄米換算・定期将来確保 SQL手順（ローカル検証版／本番適用保留）

**今は本番で実行しないでください。** 追加仕様に更新したローカル検証版です。令和8年産の締切年は回答待ちで、期限月のデータをSQLに設定していません。既存のSupabaseに追加する設計で、別のDBサービスは不要です。本番接続・実行・旧データ変換はしておらず、本番スキーマ適合性を保証しません。旧配布ZIPは廃止扱いです。

対象は `nino-0813/honma_nextjs` の既存Supabaseのみ。バックアップと復旧手順、既存トリガー/RLS、作業時間・担当者、明示的な本番承認が必要です。SQL Editorで対象プロジェクトを確認でき、DDLを実行できる担当者が扱います。サイト管理者のログイン権限とは別です。秘密情報をチャットに貼る必要はありません。

v1適用済み環境では1・2を再実行せず、既存v1の構造と履歴を確認して2aへ進みます。`migration_add_inventory_system.sql`の旧在庫3表が前提です。不足時に旧migrationや権限修復を自動実行しません。旧migrationは既存ポリシーを再作成するため、必要なら別途レビュー・承認が必要です。

事前確認が失敗する、出力が想定と違う、既存トリガーやRLSに競合がある場合は中止します。成功表示だけで本番適合を保証しません。構造以外にもステージングで既存購入、Stripeモック、管理者/非管理者アクセスを確認してください。SQLはそれぞれBEGIN〜COMMIT全体を単独実行し、途中再開・無条件の再実行はしません。エラー時はロールバック状態を確認してください。

## 追加仕様の作用

- v1の4表に加え、`kg_harvest_rules`（銘柄・年産別期限月）、`kg_raw_baselines`（人が確認した玄米基準）、`kg_contract_plans`（確認済み契約アンカー）、`kg_delivery_slots`（発送回と注文対応）の4表を追加。
- v1スナップショットと台帳に`accounting_version`を追加。既存行は1のまま。台帳の数値はkg小数6桁へ拡張するが、数値を係数で換算しない。新規原料計上は2。v1行は削除せず、玄米集計には混ぜない。
- 製品の構成品に`milling`を指定: `white`=1.1、`partial`=1.05、`brown`=1。新規通常注文にも適用。設定のない商品・古い明細は未判定。Ricekeep等の非米は明示除外。
- 新規通常注文は支払済みでも未発送なら確保。発送時に使用へ振替。発送済み返金は自動入庫しない。
- 定期注文は発送回との明示的な照合後、予測を解除し実注文の確保/使用へ置換。契約だけの予測と注文分を二重加算しない。作成済み注文の内容や発送済み構成は契約変更で書き換えない。
- 契約状態/周期/商品/数量/予約変更/スキップを変更すると、未紐付けの将来回を差分更新。スキップは既存の1か月延期を維持。予約変更の選択肢組合せを一意に特定できない場合は未判定にして旧確保を保持する。
- `paused`、pause_collection、不明な休止状態、非月次周期、期限月未設定、複数商品契約などは確認が必要。発送予定日を過ぎた未紐付け回も消さず要確認にする。
- 追加トリガーは `subscriptions.kg_subscription_changed`、`kg_product_specs.kg_spec_changed`。既存kg用capture/sync関数を原料方式に更新する。kgと無関係な既存トリガーは変更しない。

新表/RPCは既存`profiles.is_admin`による管理者限定。既存ユーザーの権限、旧表のRLS、subscriptionsの既存ポリシーを変更しません。既存管理者がsubscriptionsを読めない環境では権限を自動拡張せず停止してください。

## データ確認と初期設定

1. 期限年のユーザー確認後、管理画面で銘柄・年産の最終発送月を設定する。期限月を含む。2027年等を自動設定しない。
2. 商品/選択肢を明示的な銘柄・年産・製品kg・精米区分へ設定。例: `[{"season_id":"確認したUUID","variety_key":"koshihikari","unit_kg":5,"milling":"white"}]`。
3. 年産・品種ごとの玄米**総入庫**、移行前のEC以外の使用済み/確保を原記録に基づき一度だけ登録。現在庫を総入庫欄に転記しない。旧値が精米基準か玄米基準か不明なら未確認のままとする。基準値の後日訂正は理由付き調整で扱う。
4. 既存EC明細と基準値を重複させない。過去明細は年産・精米方法・発送証拠を個別確認する。既存v1の確定スナップショットをv2に再解釈する自動機能はないため、v1適用済みで履歴がある場合は別途照合・移行計画が必要。
5. 契約の初回/再開発送日、商品選択肢、数量、休止状態を確認して発送回を作る。契約の現在値と予約変更を取り込む。生成した回と既存注文を請求・出荷証拠に基づき1回ずつ紐付ける。予定日から勝手に実発送を推定しない。
6. 不明な契約/明細/基準が残る間、販売可能は未確定。kg不足による購入受付停止は実装していない。

注文のkgトリガーは注文トランザクション内で動くため、エラーやロックが購入書込へ影響し得ます。契約/商品予測トリガー内の再計算失敗は旧確保を保持して要確認にする設計ですが、すべての本番障害を防ぐ保証ではありません。データ設定途中でも「購入処理に無影響」とは断言しません。

## 緊急停止・再開（完全なロールバックではない）

通常手順で4・5を続けて実行しないでください。未編集ならガードが例外で止め、変更しません。承認を得た必要時だけ、DO内比較左辺`'NOT_APPROVED'`を、停止時は`'STOP_KG_ORDER_TRIGGERS'`、再開時は`'RESUME_KG_AFTER_RECONCILIATION'`へ変更します。

停止対象は`order_items.kg_capture_item`、`orders.kg_order_changed`、`subscriptions.kg_subscription_changed`、`kg_product_specs.kg_spec_changed`の4本。商品構成検証、既存SKU等のトリガー、新表、履歴、RLSは保持。ロック取得は5秒でタイムアウトします。実行後の時刻と4本のD状態を記録し、通信断等で不明なら状態を先に読み取り確認します。

v2画面はレポート内の停止状態を読み、古い数字と編集フォームを非表示にして「kg在庫連動を停止中」と表示します。ただし管理者の直接RPC/SQL操作まで一律に封じるものではないため、停止中の在庫編集と数値利用を運用として禁止します。v1コードへ戻すだけではトリガーは止まらず、v1画面は停止表示に対応しません。

停止期間の注文追加/変更/削除、入金、出荷、取消、返金、契約変更/スキップを原記録と照合します。特に「停止中に出荷→返金」は現在の返金状態だけで出荷を復元できません。未紐付け注文、既存スナップショットとの差、変更前後の予測を個別に検証し、対応できない履歴は別途修復計画と承認を用意します。機械的な過去注文一括換算・再計上はこの一式に含みません。

再開後も過去イベントは自動再生されません。停止/再開境界の処理中注文を含めた照合と、重複/欠落の差分確認が必須。3を再実行して構造確認し、正確な数値として使うのは照合完了後です。
