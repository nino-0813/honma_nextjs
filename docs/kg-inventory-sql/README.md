## 事前確認・適用の進め方

1. 対象プロジェクト名を確認し、バックアップと復旧方法、作業担当、作業時間を確定する。注文書込にトリガーを追加するため、検証用の隔離環境で先に試す。
2. `01-preflight.sql`を単独で実行する。`BEGIN TRANSACTION READ ONLY`内で構造だけを参照する。顧客・注文の行データ、環境変数、秘密情報、関数本文は出力しない。ポリシー条件はハッシュのみ出力する。
3. **例外、必須列/型の差、既存トリガーとの競合、想定外の制約/RLS/権限があれば中止。** 通っただけで本番適合を保証しない。所有者・既存ポリシー・既存トリガーの具体的動作は担当者が既存実装と照合する。事前SQLは権限を修復しない。
4. 旧 `inventory_seasons` / `inventory_varieties` / `inventory_external_sales` の導入済みを前提とする。不足時に旧migrationをこの一式から自動適用しない。旧migrationは既存ポリシーを再作成するため、別に確認・承認が必要。
5. 注文経路（カード、銀行振込、期限切れ、定期、取消、発送、返金）をステージングの外部サービスモック/テストモードで確認し、migration承認後に2を単独実行。`BEGIN`～`COMMIT`一括で実行し、途中から再開しない。エラーならロールバックを確認して原因を調べる。新表が既にある場合は再実行禁止。
6. 3を実行。既存管理者と非管理者の画面/RPC権限もステージングで確認する。SQL構造検査だけでは実ユーザーのJWTや全既存RLSの動作は保証しない。
7. Supabaseの関数公開情報に反映されることを確認し、管理画面の「新しいkg管理の準備状況を再確認」を使用。反映されない場合、権限を緩めたりmigrationを再実行せず担当者に確認する。
8. 商品/選択肢の構成品、銘柄、年産、重量基準、Ricekeep等の非米商品除外を設定。旧収穫量・販売実績・EC注文と手動確保の重複を照合。過去注文は勝手に年産を推定せず、証拠に基づいて個別確認する。一括バックフィルは含まない。

## DBへの作用と購入処理

新表は`kg_product_specs`（商品構成）、`kg_item_snapshots`（購入時点）、`kg_movements`（差分台帳）、`kg_legacy_reviews`（旧確保照合）の4つ。旧テーブルの行や列は書き換えない。

新トリガーは`kg_validate_spec`（商品設定検証）、`kg_capture_item`（order_itemsの追加/更新/削除後）、`kg_order_changed`（ordersのpayment_status/order_status更新後）。台帳は注文と同じトランザクションで更新される。**kg不足で購入を停止する仕組みはないが、トリガー内のエラーやロック競合が注文書込に影響する可能性はある。設定・照合途中だから無影響とは保証しない。** 既存決済・SKU在庫・定期課金のアプリコードは変更していない。

RLSは既存の`profiles.is_admin`で判断。新規管理RPCには管理者検査。匿名アクセスは追加せず、内部トリガー関数は一般利用者から直接呼べないようにする。レポートはSECURITY INVOKERで既存読取権限を尊重する。新表/関数の権限を設定するが、旧表のRLS、管理者指定、認証設定は変更しない。

DB適用前のコードは旧画面を参考集計と明示して再利用する。認証・通信失敗では旧画面へ切り替えない。DB適用後も未判定が残る場合、販売可能量を確定値にしない。

## 緊急停止と再開（完全なロールバックではない）

- 注文連動で障害が疑われる場合、担当者が承認を得て4を実行。`order_items.kg_capture_item`と`orders.kg_order_changed`だけをDISABLEにする。SKU等の既存トリガー、商品設定検証、新表・関数・RLSは保持する。DDLのロック取得は5秒でタイムアウトし、失敗時は勝手に片方だけ停止せず状態を確認する。
- 実行結果の`stopped_at`と両トリガーが`D`になったことを作業記録へ保存する。タイムアウト・通信断なら結果不明として、pg_triggerの状態を読み取り確認してから判断する。データをDROP/DELETEしない。3は有効状態を要求するため停止中は意図的に失敗する。
- **停止しても新画面が自動的に旧画面へ切り替わることはない。kg_reportは残り、台帳が古いまま表示され得る。** 停止中はkg画面の数値を販売・出庫判断に使わず、管理者へ停止を周知し、照合が終わるまで在庫編集と数字の利用を止める。コードだけ戻してもトリガーは停止しない。
- 停止期間の注文・明細の作成/編集/削除、入金、キャンセル、発送、返金を別途承認された方法で一覧化し、原記録と出荷証拠に照合する。停止時・再開時の境界に処理中だった注文も含める。
- 新規明細はスナップショット欠落として個別解決する。既存スナップショットの数量・構成変更や削除は自動で再解釈しない。特に「停止中に発送→返金」は現在の返金状態だけでは復元できず、出荷証拠が必須。既存の訂正フローが対応できない明細は担当者が修復計画を作成し、別途承認を得る。機械的な全件再集計や過去注文一括更新をこの一式には含めない。
- 5は承認・照合後だけ実行。ENABLEしても停止期間のイベントは再生されない。注文の流入が続く場合は、照合対象の境界時刻を定めて二段階で差分確認し、再開後に取りこぼし・二重計上を検査する。3を再実行し、照合済みになるまで数字を確定扱いしない。
