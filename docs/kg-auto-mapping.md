# Supabase注文データによる在庫紐付け

2026-10-28追加。Supabaseのプレビュー・一括反映処理と、管理画面からの操作を追加した。
ユーザーよりSQL適用とプレビュー成功の報告あり。本番の一括反映は実行していない。

## 管理画面での操作

在庫システム → お米 → 詳細設定・過去データ → 「過去注文を自動で振り分け」。

1. 判定範囲（選択中の年産／登録済みの全年産）を選び「自動判定する」。判定結果の保存だけで、在庫は変更しない。
2. 判定理由、お米／お米以外の明細、年産別・品種別の玄米換算対象量を確認する。候補は20件ずつ表示。
3. 候補全体と手動計上・開始残高との重複を確認してチェックし、理由を入力する。
4. 「確認済みの残りN明細を一括反映」。1トランザクション100件ずつ、画面で進捗を表示する。
5. 必要なら「次の100件へ進まず停止」。実行中の100件は完了する場合がある。
6. 完了後「在庫表示を更新」。エラー・再読み込み後は「保存済みの処理状況を再取得」して、再確認後に残りを反映する。

表示フィルターは確認用であり、反映対象の絞り込みではないことを画面に明記。反映対象は固定したバッチ全体。
通信エラーでは自動再送しない。DBの処理済み位置を再取得するまで再反映を無効化する。
画面を開いただけでは判定・台帳書込をしない。非管理者はRPCと保存済みバッチの閲覧を拒否する。

## 確定した商品ルール

- 3品種お試しセットはコシヒカリ・にこまる・亀の尾を各300g、1袋ずつ。商品重量の合計900g。
- 白米・玄米とも袋の重量は300g。白米の玄米換算は各0.33kg、玄米は各0.30kg。注文数量を掛ける。
- 2合×5個の単品種セットとは別商品として扱う。後者の重量ルールは今回自動登録しない。
- 年産は購入時の商品名に保存された「令和N年産／20NN年産」で確定し、登録済みの年産へ紐付ける。
- 年産なしのお試しセットは、画像や現在の日付から年産を推定しない。

## 判定の安全条件

- 商品名・選択肢・数量・注文状態はSupabaseの保存値から読む。
- 商品名が購入時と現在で異なる場合は要確認。選択肢は同じ商品ID・グループID・選択肢IDで一致する1件だけ採用する。
- 現在の選択肢対応表は過去時点の証拠とは限らないため、初回の一括反映前に対応表を管理者が照合する。
- 移行内訳がある場合は精米方法と数量合計を照合。同じ精米方法のみなら候補、複数精米区分・不一致は要確認。
- 定期便、親注文のStripe定期ID、年間契約の名称を確認し、いずれか該当すれば自動計上しない。発送予定との二重計上を防ぐ。
- 既存スナップショット／在庫履歴は上書きしない。返金・取消は発送証拠を確認するまで自動処理しない。
- クッキー・野菜セット・チケット・ひじき・乾しいたけ・指定の保存袋は、限定した購入時商品名の条件で「お米以外」の候補にする。未知の商品は一律除外しない。
- 既存の手動販売・開始残高の使用済み量に含めたEC注文を、もう一度追加しないこと。確認の明示指定が必要。

## 適用手順

対象DB・バックアップを確認し、`migration_add_kg_auto_mapping.sql` を適用する。
kg在庫v2導入済みのDBが前提。このSQLの定義だけでは注文・在庫は変更されず、新規注文用の自動実行トリガーも追加しない。

### 1. 読み取りだけで判定

```sql
SELECT x->>'status' AS 区分, x->>'reason' AS 理由,
       x->>'harvest_year' AS 年産, count(*) AS 明細数
FROM public.kg_auto_mapping_preview() x
GROUP BY 1,2,3 ORDER BY 1,2,3;
```

ready＝通常米・お試しセットの候補、exclude＝お米以外の候補、review＝要確認。
SQL EditorのDB管理者、またはログイン済み管理者だけが実行できる。

### 2. 確認対象を固定して保存

```sql
SELECT public.kg_auto_mapping_prepare(2026);
```

2026年産のreadyと全年産共通のお米以外excludeをバッチに保存する。在庫はまだ変わらない。
`NULL`を指定すると、年産を確定できた全年度のreadyを候補に含める。年度の推定はしない。
戻り値のbatch_idを控え、保存された内容を確認する。

```sql
SELECT x->>'item_id' AS 明細ID, x->>'order_number' AS 注文番号,
       x->>'title' AS 商品名, x->>'status' AS 区分,
       x->>'quantity' AS 数量, x->'components' AS 商品重量内訳
FROM public.kg_auto_mapping_batches b
CROSS JOIN LATERAL jsonb_array_elements(b.candidates) x
WHERE b.id = 'ここをbatch_idに置き換える'::uuid;
```

### 3. 確認できたバッチを反映（在庫が変わる操作）

実際の内容と手動在庫との重複を確認してから実行する。単なる画面テスト目的で実行しない。

```sql
SELECT public.kg_auto_mapping_apply_batch(
 'ここをbatch_idに置き換える'::uuid,
 '購入時情報・選択肢対応を照合し、手動計上との重複がないことを確認',
 true,
 100
);
```

100件ずつ処理。同じコマンドをremainingが0になるまで繰り返す。完了後の再実行は追加計上しない。
保存後に商品・注文・数量・精米区分・年産が変わっていたら、その100件はまとめて中止して再プレビューが必要。
既存明細はスキップし、確定後の上書きや履歴削除はしない。
理由・実行者・照合時の指紋をスナップショットに保存する。

## 今回は含まないもの

- 新規注文の無人自動判定。
- 年産なしの52件のお試しセットの自動年産割当。
- 定期便147明細の一括リンク、異なる精米区分が混在する移行明細の自動分割。
- 手動計上と過去EC注文の同一性を推測した相殺。

上の件数は提供された2026-10-28のCSV時点。最新のプレビューで再確認する。

## 検証

3品種の300g配分・精米係数・年産分離・内訳整合・例外の保留・権限・バッチ再開・再送の二重計上防止・変更後プレビュー拒否・発送後返金の扱いを検証する。
実本番の台帳照合、管理画面操作は別途必要。
画面側のプレビュー／必須確認／理由／SQL不足／変更エラー／再開／複数チャンク／明示更新／範囲切替をjsdomで確認。
