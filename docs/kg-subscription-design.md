# 定期便の将来確保・玄米換算：読み取り調査と設計案

2026-10-20。ローカル設計段階。新仕様はmain未公開、DB未適用。現行公開は旧画面フォールバック修正版 `80ccf6a`（production READY確認済み）。旧SQL一式は新仕様の本番投入用ではなく保留。

## 確定事項 / 確認待ち

- 玄米換算 = 製品重量 × 数量 × 精米係数。白米1.1、分づき1.05、玄米1。通常販売にも適用する想定。保存袋は対象外。
- 配送サイクルを重量の倍率にせず、初回発送日・周期・期限月から発送回を列挙し、回ごとの原料量を合算する。期限月を含む。
- 12月初回・2か月周期・9月まで: 12/2/4/6/8月の5回。5kgなら製品25kg、白米原料27.5kg。
- 11月初回・3か月周期・10月まで: 11/2/5/8月の4回。10kgなら製品40kg、白米原料44kg。期限月を含めても、この周期では10月便はない。
- **確認待ち**: 令和8年産の期限はコシヒカリ/亀の尾が2027年9月、にこまるが2027年10月でよいか。テストには仮の日付を入力するが、実運用設定やmigrationの固定値にはしない。
- 年産別の旧入庫量の玄米換算は自動実行しない。現在の単位・玄米/精米基準を管理者が確認するまで基準未確定とする。

### 実装前に対処が必要なコード上のリスク

`stripe-webhook`の定期注文複製は元明細を`{...it}`でコピーし、id/created_atのみ除去している。shipping_status、shipping_carrier、tracking_numberを初期化していないため、元明細が発送済みなら新しい明細にも発送済み情報が引き継がれ得る。現行kgトリガーは定期明細を自動確定しないが、新しい自動連携ではこのまま出荷実績と扱ってはいけない。新規発送回の初期化修正と回帰テストが先に必要。既存の該当注文を一括訂正せず未判定にする。

## 提案する計上モデル

1. 原料計算は構成品ごとに製品重量、数量、精米方法、係数、原料重量、年産・品種を保存する。商品名や選択肢ラベルの曖昧な推定を使わず、選択肢IDに明示設定を持たせる。混合セットは構成品別。通常注文も同じ換算を使う。
2. 1g×1.05=1.05gを丸め落とさないよう、内部は整数mg（DBならkg小数6桁相当）。係数は110/100、105/100、100/100で計算。表示精度と旧台帳（kg小数3桁）の移行は改訂migrationで扱う。過去台帳を係数で一括掛け直さない。
3. 発送回を契約明細ごとの永続IDで管理する。予定日変更だけでIDを作り直さず、スキップ前後の対応を残す。推奨構造: 契約明細版、発送回、発送回と注文/請求明細の紐付け、発送確定イベント。各イベント/紐付けに一意制約を持たせる。
4. 一つの発送回に `予測のみ → 注文作成済み → 発送済み` の排他的計上を持つ。注文ができたら予測を同じ原料量の注文確保に置換し、二重に足さない。支払済み未発送も確保。発送時に確保から使用済みに移す。発送済み・返金済みでも勝手に入庫しない。
5. 旧版の「paidを使用済み扱い」から表示分類を改める必要がある。販売可能 = 確認済み玄米入庫 + 調整 − 発送/手動使用済み − 注文確保 − 未作成将来確保 − EC以外確保。各項目は重複させない。
6. 品種/重量/精米/周期変更は適用発送回以降の未作成予測だけ再計算。発送済みスナップショットは固定。既に作成された注文は注文時点の内容を維持し、明示的な注文変更を別途受けた場合だけ差分処理する。
7. 解約は未作成の将来予測を取り消す。作成済み未発送注文の返金・取消は注文の実状態に従い、契約解約と混同しない。期末解約は権利期間/締切に対応する回まで残す。日付だけから曖昧な回を決めず未判定へ回す。
8. 原料換算未設定、発送回との対応不明、複数明細の対応曖昧、休止状態不明、同期不整合は未判定。欠落分をゼロ扱いせず販売可能を未確定にする。既存subscriptions読取の管理者RLSがない環境でも権限を自動拡張しない。

## 未確定点と次の実装範囲

- ユーザー確認待ちは令和8年産の具体的な期限年。旧入庫の玄米基準確認は移行時の作業として必要。
- 技術的に必要: 発送回IDと契約明細IDの永続化、初回/継続注文との紐付け、出荷スナップショット、予約変更/スキップの版履歴、メタデータ同期保護、複製時発送情報の初期化。
- 重量変更は現行拒否条件を変える必要がある。価格/Stripe更新への影響もあるため、在庫計算だけで対応済みとはしない。新しい決済処理変更はモック回帰検証と別途公開確認が必要。
- 週次/隔週は現行が請求日を発送予定の代用としており、実発送アンカーを確認できない契約は未判定。月次系の確定日程だけから安全に始める方針。
- 新SQLは旧一式のまま適用しない。新しい表/列/精度・トリガー・停止時の画面表示まで含めて改訂し、事前/事後/緊急停止・再照合テストも更新する。
