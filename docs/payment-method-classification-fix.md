# 決済方法と完了メールの誤判定修正（2026-10-22）

## 原因と変更

銀行振込が有効な通常決済は、PaymentIntentの`payment_method_types`が`['card', 'customer_balance']`となる。これは使用可能な支払い方法であり、利用した方法ではない。従来はcustomer_balanceを含むだけで銀行振込と判定し、Supabaseのpayment_methodと送信テンプレートを銀行振込にしていた。

決済成功時は最新Chargeの`payment_method_details.type`を参照する。展開済みChargeならその値を使用し、IDだけならStripeへ取得する。Chargeに情報がない場合は、実際の`payment_method`のtypeを取得する。customer_balanceのみアプリ側のbank_transferに対応づけ、それ以外は実際のtypeを保存する。注文に既に保存された方法や選択可能な方法の一覧は、成功時の分類根拠として使わない。

実際の支払い方法が不明、またはStripeから取得できなければ、支払い状態・メール・在庫の変更より前に500を返す。同じイベントが再送されても未払いの注文は再試行できる。既に処理済みの同一イベントはメールや在庫の副作用を繰り返さない。

銀行振込の受付・一部入金の処理、金額照合、定期購入の作成、在庫処理は今回の変更対象外。

## 検証

- カードと銀行振込が両方利用可能でも、実取引がカードならcardと通常メールを選択。
- 実取引がcustomer_balanceならbank_transferと銀行振込入金確認メールを選択。
- 注文にbank_transferが保存されていても、成功時の実取引がcardならcardを保存。
- 展開済みCharge、Chargeの取得、PaymentMethodによる補完、取得失敗、方法不明を検証。
- 実webhookハンドラーをStripe/Supabase/Brevoのモックで通し、保存値とメールのテンプレート、再送時の重複防止、取得失敗後の再試行を確認。
- 既存を含む81テストと型チェック成功。実際の決済・メール送信・注文データ更新は行っていない。

## 既存注文

この変更で過去の誤分類や送信済みメールは自動修復されない。問い合わせ対象のORD-261021-4038を含め、Stripeの実取引と注文を照合してから、注文の支払い方法の訂正や顧客への案内を別途判断する。Webhookの再送によって過去のメールを送り直す運用は行わない。
