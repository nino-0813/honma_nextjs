# 在庫管理の操作画面の改修（2026-10-20）

元の在庫画面の品種別残量カードを軸に、日常操作と初期設定を分離した。

## 操作

1. 「在庫一覧」：年産ごとの総量・品種別残量と残量バー。玄米基準では注文済み未発送、定期将来確保、その他確保を区別する。未判定・基準量未確認があるときは参考残量と明示し、追加販売量を確定しない。
2. 「入出庫・販売履歴」：入庫、直売、卸、贈答、自家用、調整と増減履歴。原料版では製品重量と精米区分から玄米換算する。
3. 「定期便の発送予定」：契約別の未注文回数・玄米確保量、日付別の品種・商品重量・数量・精米・原料重量。契約の初回/再開日確認と実注文との照合もここで行う。
4. 「設定・過去データ」：年産追加、締切、初期玄米量、商品対応、過去注文の照合。未判定一覧は検索と20件ごとのページングにした。

商品対応は、実商品から取得した選択肢、年産、品種、製品kg、精米方法を日本語で選ぶ。構成品を追加して混合セットも登録できる。JSONの入力は不要。米ではない商品は明示的に除外する。過去明細は数量をDB側で掛けるため、入力は1個分。旧形式の選択肢・旧基準スナップショット・確定後の変更は推測で再保存しない。

## 確定した締切

ユーザー確認済み：2026年（令和8年）産のコシヒカリ・亀の尾は2027年9月、にこまるは2027年10月。締切月を含む。

該当年産の締切フォームの初期値に使用する。登録済みの値を優先し、他の年産に推測値は入れない。画面を開くだけではDBに書き込まない。管理者が根拠を入力して保存した時点で既存の締切保存RPCが再計算する。

## DBとの対応

- 初期kg版でも新UIを使える。玄米・定期の拡張が未導入なら明示し、既存の記録単位を保持する。
- 初期kg版の商品対応は選択された製品kg×精米係数をunit_kgとして保存。拡張版は製品kgとmillingを保存し、DBが玄米換算する。二重に係数を掛けない。
- 玄米・定期版には既存の`migration_add_kg_subscription_reservations.sql`が必要。今回のUI変更ではSQL・本番DB・既存履歴を変更していない。
- 解約・変更・スキップ・発送時の台帳計算は既存拡張の処理を利用する。未照合の実注文、複数定期明細、旧スナップショット等の制約は`kg-subscription-implementation.md`に従う。顧客向け重量変更の既存制限は維持する。
- 過去の注文の年産や精米は記録を確認して個別に保存する。一覧の検索だけで自動分類や一括確定はしない。

## 検証

商品選択肢の読込失敗時の保存防止、選択肢IDの保存、初期版/原料版の換算、過去明細の数量、確認済み締切の初期値・保存をモックで検証。既存の購入・フォールバック・契約同期・計算テストも実行。

架空の3品種在庫と5回発送の契約を用い、1440px/390pxで在庫一覧・設定を確認。白米5kg→玄米5.5kg、5回→27.5kgを表示。ページ横溢れとコンソールエラーなし。本番のデータ連携は検証していない。
