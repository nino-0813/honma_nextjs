# 初回発送日の異なる定期商品の請求

2026-11-13。新規購入の再発防止。既存契約の変更・追加請求・マイグレーションは実施しない。

## 動作

- 月単位の定期便は、各商品の初回発送日をJSTで算出する。初回日が異なる場合のみ、発送日別のStripe契約を作成する。同じ初回日のカートと週次・隔週は従来の単一契約を維持する。
- 月1回の例：10月15日初回の商品は11月10日から継続請求、11月15日初回の商品は12月10日から継続請求。2か月ごとならそれぞれ12月10日・翌年1月10日。
- 初回決済は一括のまま。購入画面は初回発送日を商品別に表示し、送料は発送単位で既存の配送方法・地域・数量・箱割りから計算する。利用者が選んだ別配送先も適用。通常カートの送料処理は変更しない。
- 送料の按分で合計を維持する案は採用しない。ユーザーは「発送ごとに送料を再計算」を選択。新規の混在注文では購入前に別発送の合計送料を示し、契約作成時にもサーバーで再計算し決済時送料と照合する。不一致は追加請求せず再確認扱い。
- 分割契約は元の注文IDと注文明細IDの集合をmetadataに記録する。継続注文はその契約の明細だけを複製し、同じ対象だけ在庫減算する。初回の注文を契約数分複製して売上を増やすことはしない。
- マイページと管理画面は共通の初回注文から契約ごとの商品を表示する。関連注文の初回金額は一括決済額である旨を明示する。

## 再送と異常時

- 作成前に元PaymentIntentのサーバー専用metadataへ請求計画を保存する。元明細・価格・数量・送料のフィンガープリント、各発送日、請求開始日、作成済み契約IDを保持する。購入APIではクライアントがこの予約領域を指定できないよう除外する。
- 途中失敗後は保存した計画を使う。現在の商品設定が変更されても日程・会員への請求条件を勝手に変更しない。StripeのProduct・Subscription作成は決済IDとグループIDに基づく再送キーを付ける。完了済み契約は再作成しない。
- 再送キー保持期間を越えた不完全な作成は自動再作成せず、23時間を安全側の上限として確認扱いにする。作成済み契約がすべて記録されている場合はDBへの紐付けを再実行できる。
- 初回入金を記録した後で契約作成が失敗しても503を返して再送可能とする。再送で初回の在庫・メール等を再実行しない。
- scopeや送料が不正、元明細が欠落、契約行がまだ同期されていない場合は、全商品の複製や推測した請求をせず503で停止する。

## 運用上の範囲

- 新しいDBテーブル・列や環境変数は不要。新しいStripe契約と既存subscriptions.metadataを利用する。現在の本番DB・Stripe設定は変更していない。
- 初回一括注文は複数の発送回を含むため、契約単位の発送引継ぎで注文全体を自動選択しない。初回の分割発送は注文管理の明細を確認する。2回目以降は契約別の実注文を使う。
- 新しい分割契約内に複数明細がある場合、単一商品の変更UI/APIで全商品を一括置換することは拒否する。明細単位の複数商品変更UIは今回作らない。
- 既存の混在契約・過去の未請求分を自動修復しない。入金・発送・送料を照合し、別承認後に対応する。
- Stripeのテスト環境での実API操作・実カード課金・通知送信・本番デプロイは未実施。別件の2026-11-10調査で指摘した継続請求の2種類の通知による注文重複問題は、本修正の対象外。

## 検証

- 日付・年越し・月1回/2か月/3か月、送料の地域旧新キー・箱割り・数量・無料商品の計算。
- PaymentIntent/Webhook入口からの契約分割、部分失敗からの再送、保存済み計画の復元、既存契約を変更しないこと。
- 継続請求から他の契約の商品を複製・減算しないこと、対応不明時の停止、元の一括注文の保存、metadataの偽装防止。
