# 定期将来確保・玄米換算 ローカル実装結果

コードのmain反映対象。DBは本番未適用であり、コード公開だけでは追加在庫機能は利用できません。作業ブランチ `design/kg-subscription-reservations`。締切年は回答待ちで、年産・銘柄ごとの管理者設定とし、2027年等の本番値を登録していない。

## 実装

- 玄米原料kg: 白米1.1、分づき1.05、玄米1。製品重量・精米・係数・原料重量を構成品別にスナップショット。DBはkg小数6桁、画面集計は整数mg。混合セットの各構成品を扱う。
- 通常EC注文も係数を適用。未発送は支払済みでも確保、発送で使用へ振替。直売/卸/贈答/自家用は製品kgと精米を入力し、原料量と換算根拠を履歴へ保存。入庫・調整は玄米kg。
- `kg_harvest_rules`で銘柄・年産の最終発送月を設定（期限月を含む）。`kg_contract_plans`で確認済み初回/再開日を登録し、契約の周期から`kg_delivery_slots`を生成。倍率ではなく実際の発送回を列挙する。
- 未作成の予測確保 → 確認済み注文明細への置換 → 発送済み使用、という排他的計上。定期注文を勝手に予測へ紐付けず、管理画面の照合で置換する。重複紐付けは拒否、同一契約通知は差分なし。
- 契約の品種・精米・数量・周期・予約変更・スキップを受けて未紐付け将来回のみ更新。商品設定変更でも再計算。作成済み注文・発送済みの構成は変更しない。
- スキップの既存「周期によらず1か月延期」は変更しない。変更後next_billing_atの月の15日を再アンカーとする。期限切れの未紐付け回は過去だからと消さず要確認。
- 解約は未作成の予測を解除。注文作成済み分は注文の取消/発送状態に従う。発送済み返金は自動入庫しない。
- 休止・休止情報未同期、曖昧な予約変更、期限不明などは旧確保を保持して要確認にする。再計算エラーは契約更新全体を落とさず旧確保を保持し、issueへ記録。
- 旧在庫量・旧履歴は推測換算しない。`kg_raw_baselines`へ原記録を確認した玄米総入庫・EC以外の使用/確保を一度だけ登録。v1台帳はversion=1として保存し、原料集計へ混入させない。
- 緊急停止SQLは4本の連動トリガーを停止。レポートが停止を返し、画面は古い数字・編集フォームを隠す。再開だけでは停止中のイベントを再生しない。

## 購入/課金周辺の最小修正

- 定期注文複製時は新明細のshipping_statusをbefore_shipping、配送会社・伝票番号をnullに初期化。元注文の履歴は変更しない。
- Stripe同期/webhookはDB専用current_product、pending_changes、last_product_change、shippingを保持。JSONの比較付き更新で途中に入った予約変更を検知・再読込し、3回競合したら上書きせず失敗する。webhook更新失敗は再送できるよう500を返す。pause_collectionも記録する。
- 既存課金金額計算、周期、日割りなし、スキップ処理は変更しない。
- **重量変更の顧客受付は既存制限を維持**。MyPageClientは「配送先別送料が未確定」として禁止しており、5kg→10kg時の送料が不明。検討中に緩和案を試したが採用せず、最終コードでは元の拒否を保持。在庫側の再計算は合法的に反映された重量/数量変更に対応するが、顧客向け重量変更を有効化したとは扱わない。

## 残る運用上の確認・制約（具体例）

1. 令和8年産の締切がコシヒカリ/亀の尾=2027年9月、にこまる=2027年10月かは回答待ち。未設定では予測を確定しない。
2. 「2月分の入金済み注文がどの発送回か」は既存DBに発送回IDがないため、請求書・注文・出荷記録で1回ずつ照合する。自動日付推定はしない。紐付け前は注文を二重控除せず、販売可能を未確定にする。運用は完全自動ではない。
3. 既に作成された2月分をコシヒカリ5kg→にこまる5kgに変更する場合、契約変更だけではその注文を変えない。明示的な注文訂正は既存注文画面/別途照合が必要。スナップショット後の明細変更はREVIEWとなり、旧量を維持して未確定表示。
4. 同一契約にコシヒカリとにこまるの2つの定期明細がある場合、現在のplanは契約単位であり登録を拒否。契約明細単位の拡張が必要。通常商品との混在や定期複製の非定期明細も自動確定せず個別確認する。
5. 週次/隔週は月次の15日ルール対象外。実発送アンカーを保証できず要確認。Stripe外部操作による休止も同期・確認が必要。休止期間の自動再開回は推定しない。
6. 混合セット内で年産期限が違う場合、セットの一部だけを出す推測はせず要確認。次年産構成を確認する。
7. 旧v1スナップショットの玄米換算は自動化していない。既にv1運用済みなら元原料量・精米・過去出荷を別途照合する移行計画が必要。
8. 原料基準は「総入庫」であり現在の棚卸在庫ではない。EC原料使用を旧外販使用欄にも足すと重複するため入力前に確認する。
9. トリガーやSQLは本番の全構造・全外部経路を複製した検証ではない。新規課金・実メール・実注文を作成していない。公開・DB適用は別途判断が必要。
