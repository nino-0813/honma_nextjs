# kg 在庫管理 初期版

対象: nino-0813/honma_nextjs。基点: main `37dc126`。本番DBには未適用。

## 実装

- 既存管理画面の在庫タブを使用。年産作成、入庫、直売・卸・贈答・自家用、理由付き正負調整、EC状態変更の追記台帳。
- `kg_product_specs`: 商品ID + `selected_options` の完全一致で構成品を指定。構成品に年産ID・銘柄・1点あたりkgを持つ。混合セットは複数構成品。選択肢の表示名から推測しない。
- `kg_item_snapshots`: 新規明細INSERT時の構成品と数量をDBで保存。商品設定の後日変更は注文に遡及しない。未登録商品・定期明細・過去明細は未紐付け。
- `kg_movements`: 数量×構成品kgの差分を記録。pendingは確保、paidで確保を解除し使用へ振替。重複状態通知は差分ゼロ。未出荷cancelled/failed/refundedで解除。発送を観測した明細は返金でも使用量を維持。銀行振込期限切れは既存期限切れ処理のfailed/cancelled更新で解除する（時刻のみでは解除しない）。
- `kg_legacy_reviews`: 旧手動確保のEC重複分を個別照合。EC以外の確保だけ台帳に取り込み、元のreserved_kgは変更しない。再照合・解放も差分履歴にする。
- 過去の収穫量・販売履歴は元表に残して基準量として参照。既存注文の一括バックフィルなし。未紐付けは理由を付けて管理者が1明細ずつ確認。
- Ricekeepは保存袋。商品設定で「米ではない」と明示し、構成品を空にする。未設定なら未判定に残り、米から減算しない。
- 一つのSQL文のスナップショットで全件を取得。PostgRESTの通常の行数上限による欠落を避ける。エラー時に部分集計やゼロを表示しない。
- 未判定は全年度共通の件数として表示し、販売可能を「未確定」にする。旧確保の未照合も同じ扱い。判定済み差引残は参考として表示し、負数は不足として表示。

## 公開前後の挙動

コードだけ先に公開可能。`public.kg_report` の関数未検出を確認した場合は、参考集計である旨を明示して従来画面の閲覧・編集を維持する。判定は `PGRST202` と対象関数名を含む未検出メッセージ、または `42883` と `function public.kg_report() does not exist` の組合せ。PGRST202はDB関数の公開情報への未反映も含む。認証・通信エラー、別関数やテーブルの欠落は切り替えずエラー表示。準備状況の再確認ボタンあり。既存の購入、決済、SKU在庫、定期課金、他の管理画面は変更しない。

migration適用後に機能が利用可能になるが、設定と照合が終わるまでは販売可能量は確定しない。kg残量で販売受付を自動停止しない。口コミ、袋詰め、将来の定期需要予測は対象外。

8. コード公開とDB機能の有効化は別工程。本番migration、データ変更、権限運用変更は別途承認が必要。

## 既知制約

- 作成済み定期注文は購入時情報の鮮度を保証できないため、個別確認が必要。将来配送分の確保は作らない。
- スナップショット後に商品/数量/選択肢を編集した明細はREVIEWになり、旧計上を維持する。自動再紐付け・解除はしない。証拠照合と専用の訂正フローが必要で、現版では未判定として残る。
- 未判定が一件でもあると全年度の販売可能を未確定にする。過大表示を防ぐための保守的な仕様。
- 台帳は管理画面から編集・削除不可。誤った使用実績は理由付き調整で販売可能量を補正するため、使用済み内訳そのものの訂正機能は次段階。
- 商品/構成品設定は初期版のJSON入力。年産ID・選択肢IDは実データに合わせて管理者が確認する。
- 新規注文の状態をDBトリガーで集計。時間経過だけでは状態遷移しない。期限切れジョブの遅延時は確保が残る安全側の挙動。
- 全履歴を一括取得するため、注文量が大きくなった段階でサーバー側集計と履歴ページングが必要。
